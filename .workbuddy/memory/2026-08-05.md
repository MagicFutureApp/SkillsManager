## Discover 搜索集成方案（路线 A）外部约束核对

- Cloudflare KV 免费档（官方 limits 文档 2026-04-21 实读）：读 100,000/天、写(不同 key) 1,000/天、存储 1GB/account、1GB/namespace。
- KV 只被 catalog sync 写（每同步 ≈ 17 页 put + manifest + status ≈ 20 put，两代轮换再 ~18 delete ≈ 38 ops；自动刷新受 6h TTL + single-flight 限 ≤~4 次/天）。目录页/清单读每请求 ≤2 次 KV 读（最坏不缓存），但页响应 `Cache-Control: immutable` + 桌面 FIFO 6 页进一步降读。**search 路由走 Cache API（caches.default），0 KV 读写**——这是方案刻意不为搜索落 KV 的原因（避免任意 query 打爆 KV 写）。
- skills.sh 限流（方案引用的官方文档）：已认证 600 req/min per (team,project)。cache-manager 单一 Vercel OIDC token 出口，全用户共享一桶。search 收敛手段：60s Workers Cache 去重 + 300ms debounce + 本地校验(q≥2/owner 正则) 拒绝非法不入上游 + limit clamp。429 透传 Retry-After，桌面客户端退避重试 1 次。
- **两个免费档均满足，余量极大。**

关键修复：`apps/desktop/src/renderer/features/discover/catalog-ipc-contract.test-d.ts` 的 `!` 缺失（L96/L126 调可选 `Window["skillsManager"]` 方法未加 `!`，导致 `@ts-expect-error` 被 "possibly undefined" 错误满足、对入参类型无牙）。补 `!` 后即可靠断言 `page` 应为 number、`query` 应为 string。**坏入参必须保留**，否则指令变 unused 会让 tsc 失败。

P2 真实修复（非改注释）：两处 KV 隔离测试改用独立失败 app `createSearchApp(respondWith("upstream boom", { status: 500 }))` + 全新 `q=vue` query（绕过 60s 缓存 HIT）+ 传入同一个被观测 `kv`，断言 `kv.values.size===0` 与 `put:`/`delete:` 操作数均为 0（C3 零 KV 写入）。`MemoryKv` 通过 `operations: string[]` 记录 `put:`/`delete:`，断言非永真。

环境/过程陷阱：本机 Git Bash 下 `pnpm` shim 路径损坏，验证统一用 **PowerShell**；工程师 agent 在本任务中触发一次 Max turns(50) 超限（典型 thrash：反复跑 tsc/留 `.tmppath.txt`），续跑 2 行 guard 修复即过——小改动别让 agent 跑全量 desktop 测试（better-sqlite3 ABI 问题会误红）。
- 已知小缺陷（v1 可接受，follow-up）：`skills-sh-fetch.ts` 只对 401 自动换 token 重试，**不对 429 做服务端退避/合并**；且 60s 缓存不合并并发 miss（同时到达的相同 query 都 miss → 2 次上游）。要更稳可加 detail-cache 式 single-flight 合并 + 429 感知退避。另：Worker 免费档每日调用 ~10万次/天（与 KV 无关），search 也占此轴，余量仍大；扩量升 Paid 即 Unlimited。
