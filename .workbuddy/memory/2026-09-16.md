## 抢救：沙箱 git 仓库损坏（refs/ 丢失 + dev 历史对象缺失）

- 现象：`git status`/`git rev-parse` 报 `fatal: not a git repository`。根因是 `.git/refs/` 整个目录被删（含 `refs/heads`、`refs/tags`、`refs/remotes`），git 判定仓库无效（有效仓库必须含 `refs/`）。
- 更糟：dev 分支最近一段提交对象在本地对象库也缺失——`b42731d1`(FETCH_HEAD 记录的 origin/dev)、`e54b076b`(切换Tab keep-alive)、`3e721807`(docs memory) 等 6 个提交在 3 个 pack + loose 里都搜不到；`fsck` 还报 index cache-tree 指向丢失 tree、若干 blob missing。main/cache-manager/cache-manager-v2 的尖端对象完好。
- 抢救步骤（只建文件、不动工作树、不删东西）：
  1. `mkdir -p .git/refs/heads .git/refs/tags .git/refs/remotes/origin` → git 立即重新识别仓库。
  2. 从 `logs/refs/heads/<b>` reflog 正序遍历，对每个 `to` SHA 用 `verify-pack -v`+loose 检查存在性，取**最新且对象还存在的**提交作为该分支恢复指针。
  3. 结果：dev→`a040d81b`（再往上 6 提交全丢）、main→`e76bfb89`、cache-manager→`d66ea640`、cache-manager-v2→`c015dfeac`；remote-tracking 按 FETCH_HEAD/存在性补回。
- 关键结论：**丢失的提交内容其实都在工作树/索引里**（`git status` 列出 22 个改动路径，即那 6 个提交的内容 + 未提交改动），并未真正消失。dev 上仅 `e54b076b`/`3e721807` 两个本地提交从未 push，其余至多 `b42731d1` 已在 GitHub。
- 推荐用户侧彻底恢复：`git fetch origin` 后 `git reset --soft origin/dev`（**务必 --soft，勿 --hard**，否则会丢弃工作树里那两个未推送提交的改动）；fetch 从 GitHub 补齐缺失对象。沙箱内未自动跑 fetch（涉及远端 + 网络）。
- 教训：这又是沙箱 git/junction 损坏的复发；先 `git rev-parse` 判「not a git repository」多半是 `refs/` 没了，而非 `.git` 没了。

## 修复：reset --soft 后「暂存文件看不到」——索引 blob 丢失（带 CRLF 坑）

- 现象：用户执行 `git reset --soft origin/dev` 后，觉得暂存文件"没了"，`git diff --cached` 报 `fatal: unable to read <sha>`。
- 澄清：**`reset --soft` 永不碰 index/工作树**，暂存内容没丢。真正原因是 `.git/objects` 里那 7 个已暂存文件的**内容 blob 整段丢失**（fsck 报 7 个 missing blob），git 读不出内容做 diff，造成"文件没了"的错觉。文件磁盘内容完好（`git status` 里是 `M `/`A ` = 工作树==暂存区）。
- 定位：把 `git ls-files -s` 与 `git ls-tree -r HEAD` 导出文件，`git fsck --full` 列 missing blob，用 Python（沙箱里 grep 不可用）比对，确认 7 个 missing blob 正好对应当前 7 个暂存文件。
- **CRLF 坑（关键）**：仓库开了 CRLF 自动转换。直接 `git hash-object -w <file>` 重算磁盘文件时，磁盘是 CRLF、算出的 SHA 与索引里记录的「clean 过滤器转 LF 后的原始 blob」对不上，只有磁盘恰为 LF 的文件（如 `.workbuddy/memory/2026-09-15.md`）能重建成功，其余仍报缺。
- 正确修复：`git add --renormalize -- <7个文件>`——走 clean 过滤器把磁盘内容重算成 LF blob 写回索引，正好重建原始 SHA、且不碰其他文件。执行后 `git diff --cached --stat` 正常（7 文件，215 插/51 删），`fsck --full` 缺失计数归 0，那两个未暂存文件和未跟踪文件原样未动。
- 结论：本类"索引 entries 在、blob 在 objects 里丢了"的问题，首选 `git add --renormalize`（而非 `hash-object -w`）；`reset --soft` 是替罪羊，元凶是沙箱 `.git/objects` 损坏。
