### URL 校验的一个反直觉点
WHATWG URL 解析器会在解析**前**静默删掉 `\n` / `\t` / `\r`，所以 `"https://a.com\nhttps://evil.com"` 能通过 `new URL(v).protocol === "https:"` 校验。**控制字符必须在 `new URL()` 之前用正则拦**，之后再检查就晚了。
另：`new URL("https://a.com").href` === `"https://a.com/"`，**会加回结尾斜杠** —— 若用 `.href` 做规范化，必须再去一次尾斜杠，否则下游 `withBasePath()` 拼出双斜杠。

### exports map 的 types 必须按条件配对，否则 TS1479（本轮最重要的坑）
**exports 条件是按对象键顺序优先匹配的**。若把 `types` 写成顶层第一个键，它会同时吃掉 `import` 和 `require` 两种上下文 —— CJS 消费者也拿到 ESM 的 d.ts。
- `packages/utils/package.json` 是 `"type": "module"` → `dist/esm/index.d.ts` 落在 type:module 范围内，被 TS 判定为 **ESM 声明**。
- desktop main（CJS + NodeNext）`import` 该包时 TS 认定目标是 ESM → 报 **TS1479**（"CommonJS module whose imports will produce require calls; however the referenced file is an ECMAScript module"）。
- 但运行时完全正常：Node 不认 `types` 条件，走 `require` 拿到 `dist/cjs/index.js`，那里有嵌套 `{"type":"commonjs"}`。**编译红、运行绿的典型「types 撒谎」**（`arethetypeswrong` 的 Masquerading）。
- 正解：每个条件自带 types，且 CJS 构建也要 `declaration: true`：
  `"exports": {".": {"import":{"types":"./dist/esm/index.d.ts","default":"./dist/esm/index.js"},"require":{"types":"./dist/cjs/index.d.ts","default":"./dist/cjs/index.js"}}}`

### packages/utils 的三条长期规矩
1. **src 内相对 import 一律带 `.js` 扩展名**（`export * from "./is-record.js"`，源文件是 .ts 也写 .js）。ESM 构建用 `moduleResolution: Bundler` + `declaration: true`，拆多文件后 emit 的 `.js`/`.d.ts` 会带无扩展名 import，真 Node ESM 解析会 `ERR_MODULE_NOT_FOUND`。`.js` 写法在 Bundler 与 NodeNext 下都合法，是唯一两边都安全的形式。
2. **T1 必须改子路径 exports**：`cn` 依赖 clsx+tailwind-merge 只有前端用，而 `isRecord`/JWT 是 Workers 也要用的。单入口 `.` 会让 cache-manager import `isRecord` 时被连坐装上这两个纯前端包（esbuild 能 tree-shake 代码，但 `pnpm install` 照装）。`.` 只放零依赖工具，`./cn` 独立入口。
3. **必须显式声明 `typescript` devDependency**（钉精确 `6.0.3`，跟 desktop 一致、无 `^`）。否则靠 `nodeLinker: hoisted` 蹭 desktop 的 tsc，linker 策略一变就崩。
- CJS type 冲突的解法选了「build 脚本末尾 `node -e` 往 dist/cjs 写 `{"type":"commonjs"}`」而非 `.cjs` 改名（纯 tsc 只吐 `.js`，改名要加构建步骤）。注意 `node -e` 默认按 CJS 执行、不受 package.json `type` 影响，所以里面能用 `require('fs')`。
- `types: []` 只关掉自动引入的 `@types/*` 全局包，**不影响** clsx/tailwind-merge 这类自带类型的显式 import 解析。

### 沙箱文件锁（关键环境陷阱，影响所有 install/build 验证）
本沙箱的 safe-delete/文件保护层对 `node_modules` 下任何**写/替换/删除**都 **fail-closed 拒绝（EPERM）**，且项目文件**创建后不可覆盖/删除（immutable-after-create）**。
- 后果 ①：`pnpm install` 必失败 —— 它在 prune/link 阶段要替换 `.bin` 符号链接，卡在 `apps/desktop/node_modules/.bin/vite.CMD`（`EPERM: operation not permitted`）。
- 后果 ②：`pnpm --filter @skills-manager/utils build` 同样卡（install 阶段就死）。
- 后果 ③：覆盖已存在的 dist 文件也 EPERM（首次 create 成功，二次 overwrite 失败）。
- **绕过办法**：用仓库已 hoisted 的 typescript/vitest/clsx/tailwind-merge（desktop/landing 已在用，无需 install）直接调 —— `node node_modules/typescript/bin/tsc -p ...` 与 `node node_modules/vitest/vitest.mjs run`；tsc 输出指向**全新目录**（如 `dist-verify`，绕开覆盖锁）。vitest 不要传 `--cacheDir`（此版 CACError 不认）；它默认缓存若写 node_modules/.vite 失败也只是 warn。
- **后果遗留**：被 sandbox 中断过的几次 `pnpm install` 可能把 node_modules 留在过渡态（一次 prune 了 230 包）。**用户机器上需跑一次干净 `pnpm install` 恢复**。canonical `dist` 也带 stray `dist/esm/src/*`（pre-rootDir-fix 的 emit，不可删）—— 用户机器 `rm -rf packages/utils/dist && pnpm --filter @skills-manager/utils build` 得干净树。
- 正常的 CI/开发机（无此沙箱锁）跑 `pnpm install && pnpm --filter @skills-manager/utils build && check && test` 即全绿。
