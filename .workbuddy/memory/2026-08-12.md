## 修复生产 bug：minimatch interop 崩溃

- 生产 desktop（Electron main）同步带 discovery 配置的仓库（如 mattpocock/skills）报 `(0 , minimatch_1.minimatch) is not a function`。
- 根因：`build:main` = `tsc -p tsconfig.main.json`（NodeNext，分文件落 `dist/main/`），把 `import { minimatch } from "minimatch"` 编译成 `require("minimatch").minimatch`。本地 node_modules 的 minimatch 是 v10（ESM-first，CJS 入口导出命名 `minimatch`，无 `default`）能跑；但生产 asar 捆绑的 minimatch 是「默认导出/ `module.exports = fn`」形态，`.minimatch` 为 undefined → 崩。这是 CJS/ESM interop 兼容问题，锁版本无法根治（asar 可能混版本）。
- 修复：两处（`apps/desktop/src/core/skills/skill-scanner.ts`、`apps/desktop/src/main/ipc/repositories.ts`）改成 `import * as minimatchModule`，用三路 fallback 归一 `minimatch = (module.minimatch ?? module.default ?? module) as MinimatchFn`。
- 新增回归测试 `apps/desktop/src/core/skills/skill-scanner-minimatch-interop.test.ts`：`vi.resetModules()` + `vi.doMock` + 动态 `import` 分别模拟「命名导出」与「仅默认导出（原崩溃形态）」两种 interop，断言 `scanSkillDirectory(root, ["**/SKILL.md"])` 不再抛错且返回匹配 skill。两种形态均 PASS。

## 全项目 interop 同类隐患排查

- 排查范围：Electron main 进程编译进 `dist/main/` 的全部源码（`src/main`、`src/core`、`src/db`，`build:main`=`tsc` NodeNext + `esModuleInterop`，产物 CJS、node_modules external）。
- 该进程第三方裸包导入仅：`minimatch`（已修）、`drizzle-orm`/`drizzle-orm/better-sqlite3`/`drizzle-orm/sqlite-core`（命名导入）、`better-sqlite3`（默认导入）、`electron`、`node:`。
- 实证核验（node -e require）：`drizzle-orm` 各子路径命名导出（`drizzle`/`integer`/`sqliteTable`/`text`/`uniqueIndex`/`and`/`eq`…）均为 function 且 `__esModule:true`；`better-sqlite3` 为 `module.exports=函数`（无 `__esModule`），默认导入经 `__importDefault` 正确拿到函数 → 二者均安全。
- renderer/landing/cache-manager/packages 的第三方包（`@base-ui`、`@tanstack/react-router`、`clsx`、`lucide-react`、`i18next`、`zustand`、`motion`、`embla-*`、`react*`、`tailwind-merge`、`cloudflare:workers` 等）全由 Vite/wrangler/esbuild 打包，interop 由打包器处理，不踩原生 `require().named` 坑，且均未被 main 进程引用。
- 结论：**除已修的 minimatch 外，项目无同类 CJS/ESM interop 隐患**。同类风险仅存在于「tsc 直编 CJS + node_modules external + 命名导入 ESM-first 包」这一组合；新增 main 进程依赖时按此模式复核即可。

## 修复 build 报错 TS2835（动态 import 缺 .js 后缀）

- build/main 报 `Relative import paths need explicit file extensions ... nodenext. Did you mean './skill-scanner.js'?`，仅出现在新建回归测试 `src/core/skills/skill-scanner-minimatch-interop.test.ts` 第 66、94 行的 `await import("./skill-scanner")`。
- 根因：`tsconfig.main.json` 的 `include`（`src/main`、`src/core`、`src/db`）把 `*.test.ts` 也卷进 `build:main`/`check` 的 tsc 类型检查。静态 `import "./x"` 在 CJS 模式不强求后缀，但**动态 `import("./x")` 在 NodeNext 下始终按 ESM 语义要求 `.js` 后缀**——所以只有这个用动态 import 重求值模块的测试文件触发。
- 修法（最小改动，已验证）：把两处 `import("./skill-scanner")` 改为 `import("./skill-scanner.js")`。实证：`tsc -p tsconfig.main.json --noEmit` exit 0；vitest 跑该文件 2/2 pass（Vite/esbuild 会把 `.js` 解析回 `.ts`）。
- 备选（未采用）：在 `tsconfig.main.json` 加 `exclude: ["**/*.test.ts","**/*.test.tsx"]` 把测试移出生产构建——更彻底但会让 `check` 不再给测试做类型检查（除非另建 `tsconfig.test.json` 接回）。当前选最小改动。
